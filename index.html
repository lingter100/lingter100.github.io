12,000원의 가상 카드 결제를 처리한 뒤 응답만 유실되는 상황을 시작해 보세요.
  1. 가상 잔액 30,000원에서 CARD_PAYMENT 12,000원을 처리합니다. 원장과 완료 기록은 저장되지만 브라우저 응답은 유실됩니다.
  2. 새로고침 후에는 본인의 완료 기록을 GET으로 조회합니다. POST는 1회 그대로이며 당시 잔액 18,000원을 보여줍니다.
  3. 같은 번호·내용으로 명시적으로 재확인해도 저장된 결과를 반환합니다. 같은 번호로 금액을 바꾸면 요청 충돌로 거부하고 원장 반영은 1회로 유지합니다.
  4. 조회에서 기록을 찾지 못해도 실패로 단정하거나 자동으로 POST를 보내지 않습니다.
로컬 상태로 새로고침 복구 원리를 설명하는 예시입니다. 결과 조회는 읽기만 하며, ‘같은 번호·다른 금액’은 16,000원으로 재요청하는 상황입니다.


설계 상세 보기저장 실패와 응답 유실을 구분하는 복구 흐름열기닫기
같은 명령의 동시 요청은
한 번만 반영
서버에서 처리가 끝나도 응답이 끊기면 사용자는 성공 여부를 알 수 없습니다. 재전송 때 같은 행동이 다시 실행되지 않도록 명령의 처리 기록을 남기고, 새로고침 후에는 실행 요청을 보내기 전에 본인의 완료 기록부터 확인하도록 구성했습니다.
완료 기록 조회 기준
이야기방 + 요청 번호
실행자 · 행동 · 금액 · 선택값을 별도로 대조
  • 내용 일치저장된 당시 결과 반환
  • 내용 불일치같은 번호의 다른 요청 거부
  • 기록 미확인실패로 단정·자동 재실행하지 않음
요청 번호와 내용까지 비교
이야기방과 요청 번호로 기존 명령을 찾고, 실행자·행동·금액·선택값을 함께 대조합니다. 일치하면 저장된 결과를 반환하고, 같은 번호로 다른 내용을 보내면 거부합니다. 새 번호로 이미 끝난 일회성 행동을 반복하는 경우에도 현재 진행 상태를 검사합니다.
원장과 처리 기록을 함께 저장
이야기방 행을 잠근 트랜잭션 안에서 가상 원장을 변경하고 완료 기록을 함께 저장합니다. 처리 도중 예외가 나면 둘 다 롤백되며, 실패한 요청을 다시 보냈을 때 정상적으로 한 번만 반영되도록 했습니다.
새로고침은 조회부터
브라우저가 원래 요청을 보관하고 완료 기록 GET으로 결과를 확인합니다. 기록을 찾지 못한 상태를 실패로 단정하지 않으며, 명시적으로 재요청할 때도 원래 번호와 내용을 유지합니다. 손상된 결과는 다시 계산하거나 자동 실행하지 않습니다.
당시 결과와 현재 진행을 구분
다른 참여자가 다음 행동을 마쳐도 복구 화면은 내가 실행한 당시의 결과를 보여줍니다. 완료 기록을 확인한 뒤 최신 진행으로 돌아가며, 과거 결과가 현재 잔액을 덮지 않도록 구분했습니다.
동시 요청·롤백·응답 유실 검증
  • 같은 명령 4개 동시 요청에 신규 처리 1회와 동일 완료 기록 반환
  • 서로 다른 번호로 같은 일회성 행동을 요청하면 1건만 처리
  • DB 반영 후 예외를 주입해 원장·명령·조회 결과가 함께 롤백되는지 검사
  • 서버 처리 후 브라우저 응답을 끊고 새로고침해 추가 실행 없이 결과 복구
Spring/JPA 통합 테스트와 브라우저 장애 주입으로 검증한 교육용 가상 거래 흐름입니다.

1단계 · 사전 차단으로 예약 락 진입 줄이기
정원 2명에 요청 6건을 보내는 설명용 예시에서, DB 비관적 잠금만 사용하면 6건 모두 예약 락에 진입합니다. Redis 게이트는 4건을 사전 거절하고 2건만 DB 예약으로 보냅니다. 잠금 없는 DB 사전 조회는 수행합니다. 이 예시의 횟수는 실측 결과가 아닙니다.
후속 설계 · 롤백한 트랜잭션에서 재시도하지 않기
버전 충돌 또는 FK 데드락은 롤백 후 지터를 두고 새 트랜잭션으로 재시도합니다. 첫 시도 포함 최대 3회이며, 업무 조건 실패는 재시도하지 않습니다. 최종 실패 시 Redis 임시 슬롯을 한 번 반환합니다.


설계 상세 보기비관적 잠금의 대기열에서 낙관적 잠금의 충돌까지열기닫기
거절 경로와 성공 경로를
나눠서 개선했습니다
기존 결제 준비는 중복 검사부터 예약 저장까지 공구 행의 비관적 잠금을 유지했습니다. 정원 초과로 거절할 요청도 같은 예약 대기열을 거쳤습니다. 먼저 Redis로 사전 입장을 제한하고, 남은 성공 경로의 경합은 낙관적 잠금과 재시도 경계로 나눠 다뤘습니다.
1단계 · Redis로 정원 초과 요청 사전 차단
Redis Lua의 원자적 카운터로 입장을 제한해, 정원을 넘은 요청이 DB 예약 락을 기다리지 않도록 바꿨습니다. 게이트를 통과한 요청에는 기존 비관적 잠금과 DB 제약을 유지했습니다. 사전 차단이 DB의 최종 예약 판단을 대신하지 않도록 구성했습니다.
측정 · 전체 처리량과 성공 지연을 분리
1단계 전후 모든 기록 회차의 응답은 HTTP 201 50건·HTTP 409 850건이었습니다. 거절 응답을 포함한 처리량은 3.11배, 거절 요청 p95는 1816→438ms로 개선됐지만 성공 요청 p95는 1058→1287ms로 약 22% 증가했습니다. 성공 경로는 별도의 개선 대상으로 남았습니다.
후속 설계 · 예약 경로에 @Version 적용
슬롯 예약을 GroupBuy의 @Version 기반 낙관적 잠금으로 전환했습니다. 슬롯 완료·반납 경로에는 비관적 잠금을 유지했습니다. 실제 예약 작업을 별도 @Transactional 빈에 두고, 롤백 후에는 프록시를 거쳐 새 트랜잭션에서 조회·저장하도록 분리했습니다.
추가 문제 · FK의 S→X 잠금 승격 데드락
Payment INSERT의 외래 키 확인이 공구 행의 공유(S) 잠금을 얻은 뒤, GroupBuy UPDATE가 배타(X) 잠금으로 승격하면서 InnoDB 데드락이 발생했습니다. 버전 충돌만 처리하던 범위를 ConcurrencyFailureException으로 넓혀 이 실패 유형도 재시도하도록 했습니다.
재시도 경계 · 최대 3회, 실패는 명확하게
첫 시도를 포함해 최대 3회 시도하고 사이에 5~14ms의 짧은 무작위 대기(지터)를 둡니다. 업무 조건 실패는 즉시 반환하고, 최종 예약 실패 시 Redis 임시 슬롯을 한 번 반환합니다. 데드락이 발생할 수 있는 잠금 구조는 남아 있으며, 재시도는 그 실패를 처리하는 경계입니다.
단위 테스트 · 예외별 분기 확인
버전 충돌 후 성공, 데드락 후 성공, 3회 소진 후 충돌 반환과 게이트 반환 1회, 업무 조건 실패 시 재시도 없음의 분기를 확인했습니다. 처리량·지연 수치는 1단계 결과이며, 이 후속 설계의 성능 결과로 합치지 않았습니다.

설계 상세 보기랭킹 재조회로 해결되지 않는 집계 데이터와 캐시 정리열기닫기
조회가 오래된 것인지,
저장된 집계가 다른 것인지
랭킹이 갱신되지 않는 문제를 조회 응답과 저장 데이터로 나누어 정리했습니다. 캐시된 응답을 다시 받는 문제와, 프로필 JSON에는 트로피가 있지만 랭킹용 집계 컬럼은 다른 문제를 구분해 수정했습니다.
캐시 · 매번 새 랭킹 응답을 받도록
계정 API 응답에 no-store를 적용하고, 클라이언트가 랭킹을 조회할 때마다 새 요청 ID를 붙였습니다. 이전 응답을 재사용하는 경로를 줄이되, 재조회만으로 저장 데이터의 불일치까지 해결된다고 보지 않았습니다.
집계 · 기존 프로필에서 합계 재계산
프로필 JSON의 트로피를 읽어 랭킹용 합계를 다시 계산하는 마이그레이션을 추가했습니다. 이후에는 저장 버전을 확인하는 UPDATE 안에서 프로필과 합계를 함께 갱신해 두 표현이 같은 저장 경계를 따르도록 했습니다.
동점 · 점수에 도달한 시각을 별도 보존
동점은 현재 점수에 먼저 도달한 계정이 앞서도록 도달 시각을 저장했습니다. 합계가 바뀔 때만 이 시각을 갱신해 외형 설정만 저장해도 순서가 바뀌는 문제를 막았습니다. 같은 시각이면 계정 ID로 순서를 정합니다.
마이그레이션 · 복원 가능한 정보의 경계
기존 계정의 실제 과거 도달 시각은 남아 있지 않아 기존 수정 시각으로 근사했습니다. 적용 표식을 확인한 뒤 합계·정렬 인덱스·버전 기록을 보완하고, 필수 마이그레이션 적용 여부를 API 준비 상태 검사에 포함했습니다.
검증한 정렬·준비 상태 규칙
  • 같은 점수에 먼저 도달한 계정이 앞서는지 확인
  • 외형 설정 저장 후 동점 순서가 유지되는지 확인
  • 마이그레이션 SQL의 구조와 필수 적용 버전 검사 확인
정렬 규칙은 인메모리 저장소 테스트, 마이그레이션은 SQL 구조와 준비 상태 대역 테스트로 확인했습니다.
